## 一、trace-ai 想解决什么问题

传统 APM（链路追踪）能告诉你"这个 HTTP 请求挂了"，但回答不了 LLM 应用的几个问题：

- 模型**看到了什么 prompt**？
- 它**为什么选这个工具**而不是另一个？
- 它说"根据知识库……"——**知识库到底命中了哪条**？
- 一次回答慢——**慢在 LLM 还是工具还是检索**？
- 用户投诉"答错了"——**怎么把当时的整个推理过程复现出来**？

trace-ai 用 OpenTelemetry 做底层（业界标准），在 Span 上叠加 GenAI 语义属性（`gen_ai.*`）和 KWeaver 自己的 `agent.*` 扩展，用一棵 Trace 树把上面五件事全部承载起来。**产品上的最大价值是把 LLM 系统从"黑盒"变成"白盒"**，从而支持计费审计、性能优化、错误复盘、回答可解释这四条产品能力。

### 4.1 能力一：跨语言全链路串联

**业务价值**：以前要在 Go 日志和 Python 日志里分别捞，现在一个 traceId 把全链路串起来。

**真实案例**：`traceId = de39cbe95e46cb7f28d85db9cf3a4dc9`，37 个 span，1228ms，跨 agent-factory(Go) ↔ agent-executor(Python)。

```

  │   └ Process                                                              1213.0ms
  └ v2AgentExecutorHttpAcc.Call ── 跨服务边界 ──>
      [agent-executor] POST /api/agent-executor/v2/agent/run                    44.0ms
        ├ process_options / check_agent_permission                              2.4ms

            └ invoke_agent                                                   1202.0ms
```

**这条 span 同时支撑的产品场景**：

#### 4.3.1 关键：检索类工具走的也是这条通道（schema → 实例 → 子图全覆盖）

dolphin 把"知识检索"建模成 `execute_tool`，所以 §一 / PRD 提到的"知识库命中了哪条"等价问题，在以下工具的 span 上**已经能完整回放**（实测全库计数，截至 2026-05-07）：

|---|---:|---|---|

| `查询业务A产业链数据` / `v2b` / `query_biz_data_v2` / `query_biz_supply_chain` | 399 + 371 + 201 + 3 | 业务别名（数据查询）| 同 `query_object_instance` 通道，业务命名而已 |
| `execute_tool query_object_instance` | **175** | **行级数据 + 命中分** | `arguments`: `{ot_id, condition:{field,op,value}, response_format}`；`result.datas[]`: 实例所有字段值 + `_instance_id` / `_instance_identity` / `_display` / **`_score`**（命中分） |
| `业务A产业链知识网络Schema检索` | 66 | Schema 检索（业务别名）| 同 `search_schema` 通道 |

| `get_logic_properties_values` / `get_action_info` | 5 / 4 | 字段值 / Action 信息 | 同结构 |
| `execute_tool build_memory` | 11 | memory 写入 | 同结构 |

**真实 `query_object_instance` span 截取**（取自 trace 库 `_id=kksRzp0Bg9zVXkcXbYn4`，体现"对象类 → 行级数据 → 命中分"全链路）：

```json
{
  "name": "execute_tool query_object_instance",
  "attributes": {
    "gen_ai.tool.name": "query_object_instance",
    "agent.tool.latency_ms": 41,
    "gen_ai.tool.call.arguments":
      "{\"ot_id\":\"material\",\"condition\":{\"field\":\"sku\",\"operation\":\"==\",\"value\":\"MAT-001\"},\"response_format\":\"json\"}",
    "gen_ai.tool.call.result":
      "{\"datas\":[{\"name\":\"Battery Cell\",\"sku\":\"MAT-001\",\"current_stock\":\"40\",\"safety_stock\":\"100\",\"material_risk\":\"critical\",\"supplier_id\":\"SUP-1\",\"bound_skill_id\":\"substitute_swap\",\"_instance_id\":\"material-MAT-001\",\"_instance_identity\":{\"sku\":\"MAT-001\"},\"_display\":\"Battery Cell\",\"_score\":1.3862942}]}"
  }
}
```

→ 用户问"MAT-001 的库存和供应商"，**从 trace 上能完整看到**：查询了 `material` 对象类（`ot_id`）、过滤条件（`sku == MAT-001`）、命中实例（Battery Cell, current_stock=40, supplier=SUP-1）、命中分（`_score=1.386`）。这就是 PRD 蓝图里"知识引用溯源"想要的能力 —— **schema 级 + 实例级 + 命中分**全有，只是字段挂在非标命名空间下。

> **关键发现**：`_score` 字段语义上等价 OTel `gen_ai.retrieval.document.score`，只是埋在 result JSON 字符串里。命名对齐工作可以把 `result.datas[].\_score` 抽出来双写到 `gen_ai.retrieval.document.score.*`。
>
> 限制：①载荷是 stringified JSON，OpenSearch 不能按内容做精细聚合（要用得拉出来再 parse）；②未对齐 OTel `gen_ai.retrieval.{query,document,score}.*`，按标准字段名查的产品报表会查不到。**对齐方案见 §五**。

#### 4.3.2 data_source 信息深度（"具体哪张表"能问到哪一层）

| 层 | 信息内容 | 在哪能拿到 |
|---|---|---|
| **① BKN 对象类层** | `concept_id` / `concept_name` / `data_properties[]` / `primary_keys` | ✅ `search_schema` span 的 result（trace 直接有）|
| **② vega dataview 层** | `data_source.type=data_view` + `id` (UUID) + `name`（如 `ex04_1777278611_materials`）| ✅ 同上，每个 object_type 上挂一个 |
| **③ 物理表层** | `data_source_type` (mysql/pg/clickhouse/iceberg)、`datasource_id`（连接 UUID）、`meta_table_name`（完整物理引用 `catalog.schema.table`）、`sql_str`（实际下推 SQL）、`fields[].type` | ⚠️ **不在 trace** —— 需调 `kweaver dataview get <dataview_id>` 反查 |
| **④ 实际执行层** | mysql 实例、查询计划、命中索引、慢 SQL、shard 分布 | ❌ trace 完全黑盒，需 vega/BKN OTel 埋点（见 §五）|

**实测三层串起来的物理链路**（以 `material` 对象类为例）：

```
BKN object_type "material"
  └─ data_view "ex04_1777278611_materials" (id=4554c7ba…)         ← trace 上停在这层
       └─ vega catalog "mysql_<catalog_id>"                          ← 反查 dataview 才看到
            └─ schema "supply_chain"                                 ← 同上
                 └─ table "ex04_1777278611_materials"                ← 同上
                      └─ mysql connection <datasource-uuid>          ← 同上
                           └─ 实际 mysql 实例                          ← 完全黑盒
```

**`query_object_instance` span 的 result 不带任何 data_source 信息**（只有平台元字段 `_instance_id` / `_instance_identity` / `_display` / `_score` + 业务字段），所以从命中数据本身回不到"这条是从哪个表查出来的"，只能用 `ot_id` 反查 schema 间接推。

**实操建议**：SDK 在做 `agent trace --view evidence` 时可以**自动补一跳** —— 发现 schema 召回里带 dataview id 时，并发 fetch `kweaver dataview get` 把 `meta_table_name` / `sql_str` 也填进证据链，让产品 / PM / 法务问"具体哪张表"时直接给到物理引用。这是客户端拼装的天然延伸，**不依赖 vega/BKN 服务端埋点**就能达到（已加进 [kweaver-sdk#115](https://github.com/kweaver-ai/kweaver-sdk/issues/115) 作为可选增强）。

> ⚠️ **隐私注意**：`tool.call.arguments` / `tool.call.result` **是原文落库**（未做摘要化）。如果某个工具入参里带了用户敏感信息，会进 OpenSearch。一期没做字段级脱敏。

## 五、与 PRD 蓝图的差距（产品需要明确的"做不到什么"）

> 这一节不是吐槽，是给产品做需求决策的事实底座——**先知道空缺，才能决定是补埋点还是放后续版本**。

| PRD 承诺 | 现状 | 影响 | 建议 |
|---|---|---|---|

## 六、完整 Trace 全景案例（一个故事）

> 用同一条 trace（`de39cbe95e46cb7f28d85db9cf3a4dc9`），把 trace-ai 的能力**放在一次真实用户对话**里完整看一遍。完整原始数据见 `附录-完整trace样本/01_raw_opensearch_response.json`。

### 6.1 业务剧本（用人话讲）

> **2026-05-07 10:08:00（UTC+8）**，一个 Python 脚本（`python-requests/2.32.3`）从内网 `<CLIENT_HOST>` 打到 agent-factory 的 `/api/agent-factory/v1/app/:app_key/chat/completion`，HTTP 200，**总耗时 1228ms**。
>
> 命中的是一个名为"测试助手"的 Agent（`agent_id=01KR0327YK66SBYB3PNV6J4FC3`），挂着 4 个工具（`builtin_skill_load / read_file / execute_script / _date`）。
>
> 用户问："**你好，用一句话介绍你自己**"。
>
> 模型（`deepseek-chat`，T=1.0，1607 input tokens / 25 output tokens / 1003ms）**判断不需要调任何工具**，直接回答："你好！我是你的测试助手，可以帮你加载和执行技能、读取文件、调用工具来解答问题或完成任务。"
>
> agent-factory 把这次问答写回 ConversationMsg 表，更新会话状态，触发后台 memory build 线程，HTTP 200 返回。

### 6.2 LLM 真实输入输出（来自 chat span 的 inference event）

**System prompt（节选，原文 ~1500 token）**：
```text

- 你需要：先仔细思考和分析用户的问题，然后决定由自己回答问题还是使用工具来处理问题，

- builtin_skill_load(skill_id): Load the entry information for a skill (Phase 1 — must be called first). ...
- builtin_skill_read_file(skill_id, file_path): Read the full content of a specific file ...
- builtin_skill_execute_script(skill_id, entry_shell): Execute a script ...
- _date: Get current date

[省略 ~80 行 Built-in Skill Capabilities 说明]

你是一个测试助手
```

**User message（原文，未做任何加工）**：
```text
如果有参考文档，结合参考文档回答用户的问题。如果没有参考文档，根据用户的问题回答。
```

**Assistant 输出**：
```json

  "content":"你好！我是你的测试助手，可以帮你加载和执行技能、读取文件、调用工具来解答问题或完成任务。"}]
```

### 6.3 性能拆解

| 阶段 | 耗时 | 占比 | 说明 |
|---|---:|---:|---|
| 入口 HTTP `chat/completion` | 1228 ms | 100% | 端到端 |
| └ agent-factory `invoke_agent` 编排 | 14 ms | 1.1% | 鉴权、消息入库、Process 派发 |
| └ Go → Python RPC `/v2/agent/run` | 44 ms | 3.6% | 跨服务网络 + 编解码 |
| 　└ `result_output` | 1203 ms | 98.0% | Python 侧主流程 |
| 　　└ `invoke_agent`（executor） | 1202 ms | 97.9% | |
| 　　　└ `run_dolphin` | 1200 ms | 97.7% | dolphin runtime |
| 　　　　└ ★ `chat deepseek-chat` | **1004 ms** | **81.7%** | **真正的 LLM 调用** |

**结论**：**81.7% 时间花在 LLM 自身**，平台 overhead < 100ms。要降延迟只有"换更快的模型"或"加流式"两条路。

| LLM 真正花了多少 token？多少钱？ | input 9489 / output 612，按 deepseek-v3.2 单价折算 |
| 平台 overhead vs LLM 占比？ | LLM 20.2s ÷ 总 75.7s = 26.7%；其余 73.3% 是工具串行 + agent-factory 编排（步骤 7-12 五次失败导致 agent 反复试错）|

> **完整 50-span 拓扑树 + LLM 输入输出原文**见附录 [`附录-完整trace样本/04_retrieval_heavy_sample.md`](附录-完整trace样本/04_retrieval_heavy_sample.md)。

#### 6.6.3 这条样本暴露的两个产品判断

1. **数据证据链能力**：retrieval 三层（schema / 行级 / 子图）+ 命中分 `_score` 全部在 trace 上有 —— PRD 提的"知识引用溯源 / 为什么这么答"**已具备**，差的只是命名对齐（§五）。
2. **失败可观测**：5/13 步失败但 agent 自己继续推理 —— **trace 上每条失败都有 error 原文**（"技能包不存在" / "Binding Parameter Failed"），这就是 §4.4 错误根因可读能力的真实演示。LLM 最后给出"分析总结"前是看到这些失败的，所以处置建议才包含"技能包未找到"这个事实。这种"agent 拿到失败 + 仍能给出可解释回答"的链路，传统 APM 完全做不出来。

#### 6.6.4 SDK 团队额外彩蛋：`--view reasoning`

[kweaver-sdk v0.7.3](https://github.com/kweaver-ai/kweaver-sdk/pull/116) 在 spec 之外**多做了一个视图** —— 把 LLM ReAct 推理过程展开成时间序列：

### 7.1 现在能立刻做的产品功能

1. **模型用量 / 计费看板**：维度是 model × agent × conversation × 时间窗口，数据已齐。

5. **单次对话的 LLM 实输入实输出查看**（产品/PM 验证模型是否按预期回答）：在 chat span 的 inference event 里，数据已齐。

### 8.1 一键命令（封装好的子命令）

| 命令 | 走的接口 | 状态 |

| `kweaver agent trace <conv_id>` 或 `<agent_id> <conv_id>`（legacy） | 客户端 2-jump：`_search` aggregate by `conversation.id` → 拿 traceIds → `_search { terms: traceId.keyword }` 拉全量 spans，本地拼装 | ✅ **v0.7.3 已上线**（[kweaver-sdk#115/PR#116](https://github.com/kweaver-ai/kweaver-sdk/pull/116)），输出 4 视图：`--view tree / perf / evidence / reasoning / all`；`--json` 给程序消费 |

### 8.2 通用调用（`kweaver call` 直击 trace-ai HTTP API）

`kweaver call` 是 curl 等价物，自动注入 token / business-domain header。本现状文档所有 §三 数据规模、§四 实测、§4.3.1 工具清单都靠这条跑的。

```bash
# 必备 env（no-auth 平台）：
export NODE_TLS_REJECT_UNAUTHORIZED=0      # TLS 自签证书绕过
export KWEAVER_BASE_URL=https://<TRACE_AI_HOST>
export KWEAVER_TOKEN=__NO_AUTH__           # CLI 内部哨兵值，跳过 Bearer 注入

# 透传 OpenSearch DSL（最常用 —— §三 / §4.3.1 / §五 例子全靠它）
kweaver call /api/agent-observability/v1/traces/_search -X POST -d '{"size":0,"track_total_hits":true}'

# by-conversation 视图（§六 漏 span 问题用这个验证）
kweaver call '/api/agent-observability/v1/traces/by-conversation?conversation_id=<CID>'

# verbose 模式 —— 排障时**必加 --verbose** 看实际打到哪个 URL
kweaver call <path> --verbose
```

**已验证可跑通的实用 DSL 模板**（直接复制粘贴）：

```bash
# 1) 全库 span 总数

  -d '{"size":0,"track_total_hits":true}'

  "size":3,
  "query":{"term":{"attributes.gen_ai.tool.name.keyword":"query_object_instance"}},
  "_source":["attributes.gen_ai.tool.call.arguments","attributes.gen_ai.tool.call.result"]
}'

# 4) 按模型 / token 用量聚合（§4.2 计费表的取数 DSL）
```

### 8.3 配置与认证（坑过几次）

| 场景 | 正确做法 | 常见踩坑 |
|---|---|---|
| 临时连一台 no-auth 平台（不动全局状态） | `KWEAVER_BASE_URL=<url> KWEAVER_TOKEN=__NO_AUTH__ kweaver call ...` | 只设 `KWEAVER_BASE_URL` 或只用 `--base-url` flag → CLI 静默 fallback 到 active platform，没有警告（`auth/oauth.ts:1904 ensureValidToken()` 要求 token + url 同时存在才走 env 路径）|
| 切全局 active platform | `kweaver auth switch <url> --user default --global` | 不加 `--global` 会拒绝执行，提示 transient/persistent/global 三选一 |
| TLS 自签证书 | `NODE_TLS_REJECT_UNAUTHORIZED=0` 或 `--insecure` | CLI fetch 不读系统信任链，不绕 TLS 验证就一直报 `self-signed certificate` |
| 看 CLI 实际打到哪个 URL | `kweaver call <path> --verbose` | 不加 verbose，`--base-url` 被忽略时无任何提示 |

### 8.4 当前 CLI 缺的能力（产品场景视角）

| 缺口 | 影响 | 临时绕法 |
|---|---|---|
| 没有 `kweaver trace search` 子命令封装 `_search` | 跑任何 trace 聚合都要手写完整 OpenSearch DSL | 用 §8.2 模板 |
| ~~`agent trace <a> <c>` 后端 404（agent-factory 没暴露 observability 路径）~~ | ✅ **已由 SDK v0.7.3 修复**：客户端 2-jump 走 trace-ai `_search` 直查 | — |
| ~~没封装 conversation 视图的 traceId 兜底二段查询~~ | ✅ **已由 [kweaver-sdk v0.7.3 / PR#116](https://github.com/kweaver-ai/kweaver-sdk/pull/116) ship**：客户端 2-jump 拼装 + **4 视图**（tree / perf / evidence / **reasoning ⭐**）| `kweaver agent trace <cid> --view <name>` 一键开箱即用；样例见 §6.6 / `附录-完整trace样本/04_retrieval_heavy_sample.md` |
| `perf 视图累计耗时双重计数`（root 75740ms 同时算它自己 + 所有 descendants → "other 378606ms"）| 性能拆解的"占比"读起来误导 | 看相对量级（哪类耗时大）仍可参考，绝对值不可信；可向 SDK 提 polish issue（exclusive duration / self-time）|
| `--base-url` 单独不工作且无警告 | 排障时容易把 localhost 的结果误认为远端 | 一律用 env vars `KWEAVER_BASE_URL` + `KWEAVER_TOKEN=__NO_AUTH__` |
| 没有大字段安全模式（输出原始 prompt / 工具入出参 ） | 终端打印整段 stringified JSON，敏感信息可能被同事看屏看到 | `kweaver call ... | jq '.hits.hits[]._source.name'` 先脱敏再看 |
